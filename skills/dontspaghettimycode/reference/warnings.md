# Symptoms and Structural Diagnosis

A **symptom** is an observable cost or wrong behavior. A **distortion** is the wrong requirement, model, Owner, boundary, lifecycle, failure policy, or verification path that forces surrounding code or people to compensate. Treat every distortion as a hypothesis until evidence supports it; do not score a system or authorize a rewrite from a smell alone.

## Diagnose from the symptom inward

1. Trace the pinned scenario from its real UI, API, job, event, or operation through application logic, domain decisions, persistence, and external sources.
2. Mark every compensation: duplicated conditions, flags, defaults, retries, adapters, repair jobs, manual steps, compatibility branches, and test-only assembly.
3. Ask what incorrect fact, relationship, state, requirement, ownership, boundary meaning, lifecycle, failure policy, or verification path makes each compensation necessary.
4. Prefer the deepest shared cause whose correction removes several compensations. “Deepest” means closest to the governing truth, not necessarily the database or lowest layer.
5. Try to disprove the hypothesis with distinct responsibilities, generated or Derived representations, intentional snapshots, temporary migrations, measured performance needs, and explicit requirements.
6. Split the investigation when one cause cannot explain the evidence; do not force a grand diagnosis.

Stop when the supported distortion, forced compensations, correct target, and disconfirming evidence explain the pinned symptom. Size, file count, directory shape, churn, and complexity scores may select where to inspect; they never prove distortion.

## Observable symptom families

| Symptom | How it appears in the system | Inspect first | Disconfirm when |
|---|---|---|---|
| Change amplification | A small rule change needs same-reason edits across controllers, jobs, queries, schemas, or clients | Independent writers and decision sites; diffs and history for the same business question | Locations only translate, generate, migrate, test, or present one authority for distinct boundaries |
| Change collision | Unrelated rule changes repeatedly require understanding, modifying, or broadly testing the same decision surface, or one capability change breaks another | Shared mutable state and write paths; transaction and lock scope; caller-specific branches; tests that require unrelated state; history grouped by change reason | The location only composes, registers, dispatches, generates, or declares independently owned behavior, or all decisions enforce one coherent invariant or lifecycle |
| Regression cascade | Fixing one entry point breaks another path for the same behavior, or successive fixes alternate which caller is correct | Divergent call paths, duplicated conditions, bypassed validation, stale projections, and missing invalidation | Failures have unrelated causes or the affected paths intentionally implement different contracts |
| Invalid or drifting state | Impossible flag combinations, orphaned references, disagreeing totals, stale eligibility, or recurring data repair | Canonical writes, constraints, state transitions, Derived-data sources, and reconciliation history | The values are intentional snapshots, bounded-stale replicas, or separately owned facts |
| Meaning disagreement | `null`, status, units, identity, timestamps, or deletion mean different things across modules or boundaries | Source contracts, adapters, defaults, validators, persistence mappings, and consumer assumptions | Different meanings are explicit, translated once, and have distinct lifecycles or compatibility obligations |
| Sequence or failure fragility | Correctness depends on call order, timing, retries, paired calls, or cleanup; duplicates and partial success recur | Transactions, idempotency, retry ownership, resource lifetime, events, and concurrency paths | One lifecycle Owner makes ordering, committed points, and recovery explicit and tested |
| Special-case accretion | Each addition or fix puts another branch, flag, parameter, or near-copy around the same decision; conditions nest or follow the order requests arrived, and customer, date, or environment exceptions keep growing | The question the branches answer, the facts they switch on, and how each case was added | Each case is a distinct contract or changes for a different reason, or the cases already fall out of one model, table, or merged condition |
| Operational compensation | Users re-enter data, support runs scripts, or scheduled jobs repair state | Runbooks, incidents, feature flags, manual workflows, and reconciliation jobs | The mechanism is a bounded migration or deliberate operation with an Owner and removal or review condition |
| Authority confusion | Nobody can identify where a rule changes; multiple places write, translate, log, retry, or answer the same question | Every write and decision path, constraints, validators, policy calls, and reporting ownership | Each location has a distinct boundary responsibility and all underlying decisions pass through one Owner |
| Green checks, wrong system | Unit tests pass while production fails, a migration is tested against the candidate instead of the deployed prior version, or symbol searches miss surviving callers | Real bootstrap, composition root, deployed versions, caller behavior, and tests that deliberately break the claimed path | The check reaches the assembled path real callers use and fails when the claimed protection is removed or substituted |

## Structural distortion hypotheses

| Distortion | Supporting evidence | Typical compensations | Disconfirm when |
|---|---|---|---|
| Wrong requirement or invariant | Different workflows answer the same business question differently, or the existing rule contradicts confirmed target behavior | Caller-specific exceptions, UI warnings, manual approvals, and undocumented behavior changes | One explicit requirement explains the variants and each implementation follows it |
| Wrong data, relationship, or state model | Flags permit impossible combinations; one field collapses distinct facts; copies drift; absence has several meanings | Null checks, defaults, special-case branches, synchronization, repair scripts, validation scattered after the fact | The model represents each fact once, invalid states are blocked, and copies have declared semantics |
| Split or missing Owner | Multiple writers or modules independently implement one rule, transition, or default | Duplicated conditions, coordination protocols, caches of decisions, and same-reason edits | One concrete Owner decides, while other locations only translate or consume its result |
| Boundary meaning leaked inward | Wire, vendor, database, or view representations become domain vocabulary outside their boundary | Source-specific branches, shared DTOs, repeated conversions, and contract-shaped domain objects | Meanings, validation, lifecycle, and compatibility are truly identical across the reused boundary |
| Wrong abstraction boundary | One abstraction, often a god service, makes unrelated decisions share mutable state, entry points, transactions, lock scope, or caller-specific modes; or wrappers and interfaces only forward while unused modes predict imaginary variants | Cross-capability regressions, broad test setup, flags, callbacks, generic frameworks, and pass-through layers | The abstraction enforces one invariant, coordinates one lifecycle, only composes, registers, or dispatches independently owned behavior, or serves current interchangeable implementations |
| Unowned lifecycle, sequence, or failure policy | Layers independently retry, log, swallow, compensate, clean up, or decide partial success | Defensive retries, duplicate suppression in callers, fallback branches, and manual reconciliation | One Owner defines ordering, atomicity, failure translation, recovery, and observability at the real boundary |
| Permanent compatibility shadow | Old schemas, workflows, encodings, or adapters remain without current reliance, overlap, obligation, or removal criteria | Dual writes, double reads, legacy branches, and new callers added to the old path | Evidence shows a required stable contract or bounded migration with an exit condition |
| Verification path is a second architecture | Tests construct validators or services differently from production, measure the harness instead of the subject, or census symbols instead of behavior | Test-only wiring, duplicated setup, green unit suites, and repeated manual verification | The check enters through the real boundary, observes the subject, and fails under deliberate removal or substitution |
